# Cursorへの修正指示：OOOの正本・拡張性・並行開発

対象: `/Users/kk/OOO`。2026-09-11の静的確認に基づく指示です。コードの存在と実環境での有効性は区別してください。以下を調査だけで終えず、安全に実施できる修正・検証まで進めてください。

## 目的と維持する思想

- 人間が判断・最終承認し、AIAは提案・許可範囲の実行を担う。
- 正本を一つにし、UI・CLI・APIで業務処理を共有する。
- CoreとCommunityの独立リポジトリは維持する。全面的な再構築やフレームワーク変更は対象外。
- 複数IDE・開発用AIAの変更、テスト、生成物が互いに混入しないようにする。
- 業務用AIAのテナント操作と、開発用Agentのソースコード編集を区別する。

## 1. 先に現状を記録する

README.md、PROJECT-MAP.yaml、Core/AGENTS.md、Core/steward/rules/engineering/、各領域の説明を読む。
各リポジトリのHEAD、ブランチ、status、staged/unstaged/untrackedの対象パス、worktreeの登録先と実体、Git管理対象を記録する。秘密値・テナント本文をレポートに出さない。

初回報告は「実装済み／未検証／不足」とし、ファイル・行番号と影響を記載する。以下の確認済み事項も現在のコードで再確認する。旧パスが一覧にあることだけで壊れていると判断しない。

## 2. 問題台帳と修正

### P1-A: Webの編集正本、生成先、公開元が不一致【確認済み】

根拠:
- Web/package.json:6–8: buildが隣接Communityの生成処理を呼ぶ。同期はrsync --delete。
- Community/packages/shared/scripts/generate-overview-links.ts:16: 生成先がCommunity/sites/coming-soonに固定。
- Community/.github/workflows/deploy-oorgos-org.yml: 公開元はsites/coming-soon。
- Webは独立Gitリポジトリではなく、OOOトップもGit管理されていない。

修正:
1. 現在の正本指定であるWebを維持し、そのbuildでWeb自身の成果物を生成する。生成スクリプトは入出力先を明示できるようにする。buildから兄弟リポジトリへの書込みをなくす。
2. 生成にCommunityを必要とする間は依存を明記し、別環境で取得・再現できるようにする。固定された個人の絶対パスに依存させない。
3. Web→Community公開ミラーへの同期を明示的な別操作にする。生成対象との順序を定義する。
4. 同期前に対象ファイルと削除候補を提示し、ミラー側の未反映変更を検出したら停止する。無条件の--deleteで他者の変更を消さない。除外・保護対象を管理する。
5. Web正本のGit管理方法を具体案にする。新規独立リポジトリ、既存リポジトリ内への正本配置などは比較して一案を推奨するが、リポジトリ再編・正本移動は承認前に実施しない。そこ以外の修正は進める。

受入条件: Web build前後でCommunityの内容が変わらない。生成物がWeb側で更新される。同期dry-runで差分が分かり、ミラー側の未反映変更は上書きされない。Git管理と公開の未決定部分は明示する。

### P1-B: 開発用Agentに作業ツリー分離の保証がない【確認済みの経路あり】

根拠: Core/src/lib/agent-dispatch.ts:349にlocal cwd: ROOT_DIRの起動経路がある。これは当該コード内でAgent別worktreeを作成していないことを示す。SDK外部の隔離挙動は未検証。

修正:
1. この経路が業務用か開発用か、呼出元・runtime設定まで追跡する。業務用dispatchを一律Git worktreeへ変更しない。
2. 開発用Agentは1作業=1ブランチ=1worktreeを割り当てる共通の起動・検査手順を設ける。外部IDEも同じ作業ディレクトリを開けるようにする。
3. 開始コミット、対象リポジトリ、read/write/generated/denied paths、共有資源、完了条件を作業定義に記録する。
4. 起動前と統合前に範囲を検査する。完了検査はコミット差分だけでなくstaged/unstaged/untrackedも含める。範囲外変更を自動削除・復元せず、統合不可として報告する。
5. worktreeはアクセス権の隔離ではない。別worktreeへの書込みを強制的に禁止できるサンドボックスがあるか確認する。未対応なら「規約・検査による制御」と明記し、安全な隔離を保証したと表現しない。

受入条件: 2作業が別worktreeで動き、片方の未コミット変更がもう片方に現れない。範囲外の編集・未追跡ファイルを統合検査が拒否する。業務用dispatchの既存動作を壊さない。

### P1-C: テストの共有テナント競合が残る【確認済み】

根拠: Core/tests/setup-restore-protocol.ts:243付近で、復元は直列化するがテスト本体は競合し、警告のみと明記されている。

修正:
1. 作業ごとに一時テナント・DB・ログ・生成先・ポート・必要なDocker project/volumeを分離する。
2. テストの実際のパス解決と副作用を調べ、実運用テナントや共通の外部DBへ向かわないことを検査する。環境変数を付けただけで隔離できたと判断しない。
3. 同一workspaceの共有fixtureを使うテストは、テスト実行全体を適切に排他するか、完全に専用fixtureへ移す。警告だけで続行しない。

受入条件: 一時fixtureで2実行を検証し、隔離されるか、後続が待機／明確に拒否される。片方の復元処理が他方の成果物を消さない。

### P1-D: Git移行後のworktree登録の整合性【未検証】

Core・Communityのworktree一覧に旧OS_Steward、OS_Community、Documents/Codex配下が残る。
登録先の存在、各.gitの参照先、git-common-dir、どの管理リポジトリに属するかをread-onlyで照合する。正常な既存worktreeは維持する。二重登録・不一致があれば根拠と修復案を提示する。repair/prune/removeや.git直接編集は承認前に実施しない。

### P2-A: 比較用コピーが実装の正本と同列に見える【確認済み】

Console、Auth、直下tenants、operationsは抽出物を含む。Console内にも同内容を意図した複数配置がある。
各領域について正本・コピー・生成物・実行データをPROJECT-MAPへ明記し、編集先と生成責任を一本化する。抽出物に編集禁止の案内を置き、開発Agentの標準書込み対象から外す。コピーを削除・移動せずに、まず規約と検査で分離する。Auth抽出物をそのまま共通認証パッケージへ昇格させない。

### P2-B: IDE横断の開発ルールの入口が不足【確認済み】

現状、検索で確認できたAGENTS.mdはCore内のみ。OOOトップの管理資料もGit管理外。
ルートおよび必要なリポジトリに、正本、作業範囲、共有資源、隔離、検証コマンドを記す。Coreの既存セキュリティ・承認ルールを弱めず、各IDE固有設定は共通規約への参照にする。全IDEが同じファイルを自動読込すると仮定しない。起動時の規約読込手順を明示する。
管理規約のGit管理先はWebの管理方針と合わせて具体案を作る。

### P2-C: 開発パスが固定され、別worktreeに追従しにくい【確認済み】

dev-env.shは/Users/kk/OOO/Core等を固定し、ORGOS_HOMEが未設定なら常にCore正本を指定する。
worktreeから実行しても正本のデータへ戻らないように、スクリプト位置・明示指定・cwdの優先順位を定義する。既存の明示的な環境変数指定は保全する。別一時パスに配置したテストで解決先を確認する。

### P2-D: モジュール境界とCLI/Webの処理共有【一部実装済み、網羅性未検証】

Coreには分野別CLI registrarとsrc/libがある。設計ではGUI/REST/CLIが同じApplication処理を通るが、全経路の一致は未検証。
代表的な参照・変更・承認操作の経路を追い、重複業務処理やUIからの直接正本書込みを特定する。認証、入力変換、表示整形の差と業務ルールの重複を区別する。発見した具体的な重複のみ小さく修正する。
モジュールの公開入口・許可依存・循環依存を定義し、段階的なCI検査を追加する。根拠のない全面パッケージ分割は行わない。

### P2-E: 共有資源とリポジトリ間検証【不足範囲を追加確認】

package.json、lockfile、共通schema、DB migrations、認証契約、生成registry、CI設定を共有資源として列挙し、統合担当に所有させる。各Agentは提案差分を出し、同時に直接統合しない。
CoreとCommunityの既存CI・連携テストは存在するため、作り直す前に内容を調べる。SSO/API契約、Webの公開ミラー一致、領域外書込み、再現可能な依存インストールの不足分だけ補う。
Community CIのnpm installと生成・同期処理について、意図した更新かを確認し、lockfileに忠実な検証と意図しない差分の検出を行う。

## 3. 実施順序

1. 現状台帳と副作用・Git境界の確認。
2. Web生成先と同期保護、dev-envのパス解決。
3. 共通規約、正本・コピーの案内、作業定義と範囲検査。
4. 開発作業のworktree起動とテスト実行資源の隔離。
5. 特定できた依存境界・共有処理・CIの不足を修正。
6. 未決定のGit管理・移行案を具体的な対象差分とともに提示。

## 4. 保全条件

- 既存のdirty/staged/untracked変更を保持する。無関係な整形・restore・reset・clean・stash・削除をしない。
- 旧開発パス、比較用コピー、台帳、秘密情報を削除・上書きしない。
- 実運用テナントのイベントや台帳を検証用に変更しない。既存テストがそれらを触る場合は先に隔離する。
- commit、push、公開、デプロイ、認証方針変更は実施しない。この依頼は修正作業の指示であり、これらの承認ではない。
- 並行Agentを追加する場合も、先に隔離と所有範囲を準備する。共有checkoutで同時編集しない。
- 判断が必要な再編だけを質問し、独立して進められる修正は続行する。

## 5. 完了報告

artifacts/reports/に、問題IDごとの実装済み／未検証／不足、修正ファイルと行番号、検証方法・結果、残る迂回経路、承認が必要な具体案を記載する。
対象差分を開始時点と比較し、他者の変更と今回の変更を区別する。受入検証は一時環境で実施し、単なるbuild成功で並行安全性を合格にしない。
最終判定を「単独開発」「複数IDEの分離開発」「複数AIAの自動並行開発」に分け、保証できる範囲と保証できない範囲を短く示す。
